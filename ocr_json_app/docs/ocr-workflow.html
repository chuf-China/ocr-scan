01 / PIPELINE

逐行 OCR，把“版式”当成一等数据

整页 OCR 会把相邻的几行合成一段，再想还原原分行就只能靠猜。这里先用像素投影找出文本行盒，再逐行裁图识别；每一行天然带着原坐标、原字号与原换行。

本节拆解的是 llama.cpp 路线；当前首选的官方 PaddleOCR-VL 流程见架构图“路线 A”，本机实战与坑见 paddleocr-vl-guide.md。

源 PDF → 起本地引擎 → 150 dpi 渲染 → 行盒检测 → 逐行 OCR × 3 票 → 几何还原 → layout JSON → 单文件网页
01

启动引擎与页面渲染

150 dpi

run_ocr.ps1 先停掉旧引擎、拉起本地 llama.cpp 服务（默认 PaddleOCR-VL-1.6，备选 OvisOCR2）并轮询 /health；随后用 pypdfium2 把每页渲染成 150 dpi 的 RGB 图，A4 页面对应 595.3×841.9 pt。

InPDF引擎型号 → Out页面 RGB 图灰度矩阵

pypdfium2 是原生库，多线程渲染会 access violation：渲染串行，OCR 才用线程池并发。

02

行盒检测

像素投影

对灰度图做行、列墨迹投影，找出真正有墨的文本行；把填空下划线这类 2–3 px 的碎行并回相邻行，过滤噪点，再从 PDF 文字层补回字号。

In灰度图文字层字号 → Out行盒列表典型行高

行盒是后续裁图、字号、绝对定位的共同基准；这一步不依赖模型输出。

03

逐行裁图、调用与投票

0.1 – 0.3 s / 行

按行盒裁图，左右留 8 px、上下留 3 px；4 个 worker 并发调用本地 VLM 服务。每行默认 3 票，取多数文本，并记录 disagreement 与 finish_reason。

In行裁图引擎 prompt → Out文本票数分歧标记

PaddleOCR-VL 认官方前缀 OCR:，OvisOCR2 认整页 Markdown 指令；提示词不能混用。

04

几何还原：插图、表格、零交叠

原生 bbox 优先

先取 PDF 原生图形资源（嵌入图 + 矢量线/曲线/矩形并集），在行投影前把图区涂掉，再按原生 bbox 以 300 dpi 裁片；取不到原生资源时才退回“墨迹落在文字蒙版上的比例”（阈值 0.20）。表格用长直线游程找框线带。两者都不采信模型给的 bbox，裁片也不得压住任何正文行。

In页面图原生图形资源文字蒙版 → Outpt 区域盒PNG 裁片

模型曾对一页连发 11 个相同占位符，也把整页当插图；原生几何 + 像素检测才是稳定来源。涂掉图区后，Q11 这类“图在右、文字在左”的行不会再被曲线粘成 141pt 的合并行。

05

组装 layout JSON

3 行分歧

像素坐标换回 PDF 点，按 top, left 显式排序；丢弃图形区幻觉行，把页图压成 JPEG、裁片留成 PNG，一起编码进 JSON。

In行结果几何区域 → Outdocumentstatspages

本机样例：6 页、77 行、51 行含公式、5 张插图；3 行出现投票分歧。整链约 83 s（3 票 OCR）。

file:// 双击即开

04 / DESIGN NOTES

六个取舍，决定这套流水线是否可信

页面上看到的“原版式”，来自几个很具体的工程决定，而不是某个模型的一次整页输出。

逐行 OCR，而不是整页

行盒来自像素投影，天然保留原分行与缩进；每行单独裁图识别，质量更高，也避免整页模型把多行合并成段。

几何优先，不信模型 bbox

模型会把整页当插图、连发相同占位符；插图优先取 PDF 原生图形资源，取不到时再退回文字蒙版墨迹比，表格用框线游程，和 OCR 引擎解耦。

3 次投票，显式记录分歧

温度设为 0 也不是确定性的：同一张图偶尔会被输出成完全无关内容。默认 3 票取多数，同时记录 disagreement，便于抽查。

裁片零交叠

插图裁片不得压住任何正文行：判据是交叠为零，不是“占比小于阈值”。落在插图内的正文行会被丢弃，避免图上一套、文字层又一套。

提示词与定界符按引擎固定

Paddle 认 OCR:，给它自然语言长提示会退化；Ovis 反过来。公式定界符也不同，生成阅读器时必须按 document.engine 选择。

四层校验，别只看统计量

代码冒烟先保证两条流水线真能 import、3.9 语法与纯函数判据没坏；结构、渲染、内容再依次查产物。插图压住题干时，JSON 与公式校验都能通过、行重叠统计仍为 0，只有渲染层抓得到。

05 / DATA CONTRACT

一份 layout JSON，决定网页能不能复原原稿

阅读器不重新理解版面，只消费识别阶段留下的坐标契约。行坐标是 PDF 点，页图与裁片是 base64，阅读器按页宽做一次等比换算。

所有识别结果归一到同一种结构：document 记录引擎与 DPI，pages[].lines[] 记录每行文本与 pt 坐标，figures[] 记录插图/表格裁片。

坐标统一到原始页面坐标系；前端按 k = paperW / page.width 换算，因此缩放窗口时行与裁片一起缩放。

  • document.engine决定提示词与公式定界符：Paddle 是 \(...\)，Ovis 是 $...$。
  • pages[].lines[]top / bottom / left / right 为 PDF pt，左上原点；size_pt 用于前端字号。
  • figures[].pt插图/表格裁片的 PDF pt 盒；PNG 以 base64 内嵌，原位贴回。
  • stats.vote投票次数与 disagreed_lines，用于质量抽查与版本对比。

已知限制

  • 官方流程的表格是 HTML 文本，可选中/搜索；llama.cpp 路线的表格仍是裁片，需要可检索表格时走官方流程。
  • 没有原生图形资源的纯扫描件仍会漏图；原生矢量/嵌入图可直接取 bbox，取不到时才依赖文字蒙版，纯扫描件会退回“全部当正文”。
  • 字体回退：原卷字体本机未安装时会回退到 SimSun，字宽略有差异；公式与关键数字建议对照原始扫描。
  • OCR 仍是模型转录，个位错字难免；阅读器保留「原始扫描」切换，就是为了让复核回到原图。

逐行 OCR 的意义，是让每个字都能回到它在纸上的位置。
